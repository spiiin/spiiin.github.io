Intro#

Осилил статью Бориса Баткина про templates в dascript. Мне нравится dascript тем, что в нём иногда встречается код, в который можно вчитываться много раз, и каждый раз находить в нём что-то новое. Это как раз такая статья, в которой стоит попробовать разобраться. Информация в ней сильно сжата, и приправлена сложным слогом, но оно того стоит.

В ней описан пример того, как с помощью синтаксических макросов добавить в язык обработчик темплейтов, похожий на C++. Его можно развивать и дальше в сторону C++, если хочется поупражняться в понимании того, как это работает. Но на самом деле, в большинстве случаев на dascript существуют другие, более элегантные решения для большинства проблем, которые бы решались в C++ через шаблоны.

Эта статья навела меня на мысль попробовать реализовать через макросы некоторые штуки, которые мне попадались в F# (-F# in imaginery world). Особенно с учетом того, что я вкрутил себе dascript в jupyter notebook и запихал туда возможность работы с макросами (- Daslang Jupyter - dastrudel, macro workbench).

В репозитории собрал несколько таких экспериментов. Я не уверен в их практичности, но сгодятся как академические примеры того, что можно делать с помощью макросов.

Type providers#

Type providers создают типы по внешнему описанию данных. Например, схема игрока хранится в JSON, а в коде хочется работать с обычными полями и получать ошибку компиляции при опечатке в имени или несовпадении типов.

Здесь Player и его поля берутся из схемы. Получившийся тип можно передавать в функции, как обычную структуру. Провайдер читает только запрошенную схему и зависимости её полей. В библиотеке есть также простой вариант с аннотацией [json_provider] и вариант без генерации структур — с проверяемым доступом к уже разобранному JSON:

Потенциально это полезно для игровых конфигов, описаний ресурсов и данных из внешних инструментов: не нужно поддерживать одинаковый набор полей в схеме и в исходниках. Проверка схемы при компиляции при этом не отменяет проверку самих данных при загрузке.

Active patterns#

Active patterns позволяют использовать функцию-распознаватель прямо в сопоставлении с образцом. Например, распознать в строке число и сразу использовать его в подходящей ветке. Отдельный макрос для этого не понадобился — нужные возможности уже есть в стандартном daslib/match.

Так удобно разбирать команды, классифицировать события и проверять игровые условия: детали распознавания живут в отдельных функциях, а варианты поведения видны рядом. Распознаватель может вызываться повторно для разных веток, поэтому лучше обходиться без побочных эффектов.

Computation expressions#

Computation expression — это блок последовательного кода, правила выполнения которого задаёт специальный объект, builder. Макрос преобразует блок в вызовы его операций. Builder решает, что делать после очередного шага: продолжить вычисление, вернуть ошибку, дождаться результата или выполнить оставшуюся часть для каждого элемента коллекции. Bind похож на “перегруженную точку с запятой”. Интересны тем, что с их помощью можно реализовать очень различные фичи языка, от сокращения избыточного кода, до выворачивания порядка выполнения наизнанку — ленивые вычисления, ранний выход, возвраты и повторное выполнения кода, асинхронные вычисления. Таким образом, практически любой код можно заставить выглядеть линейно (если бизнес-логика, которую описывает код линейная, то чтобы она и в коде выглядела линейной), спрятав всю нелинейность внутрь билдера.

Остаток блока после bind становится продолжением — кодом, который получит успешное значение и выполнит следующие шаги. Упрощённо первый bind означает: «вот результат first_step() и функция, описывающая всё, что надо сделать дальше». Builder может вызвать эту функцию сразу, позже, несколько раз или вообще не вызывать.

Для знакомых с C++ здесь можно провести аналогию с promise_type, co_await и co_return: поведение привычной конструкции определяется пользовательским типом. Но CE охватывают и распространение ошибок, и перебор вариантов, и передачу состояния. Это универсальный протокол, через который реализуются разные способы связывать вычисления:

Builder Что происходит после bind
Result Продолжить с успешным значением или вернуть ошибку
Option Продолжить, если значение есть, иначе вернуть none
Task Дождаться завершения операции и продолжить с её результатом
List Выполнить продолжение для каждого элемента и собрать результаты
State Передать состояние следующему шагу
Parser Продолжить разбор с новой позиции во входном тексте

Builder реализуется обычными типами и перегрузками функций протокола. Можно добавить собственный билдер отдельным модулем, не меняя сам макрос CE.

Для более подробного знакомства с идеей в F# есть серия Computation Expressions на F# for fun and profit.

Где хватит обычного dascript

Универсальность механизма ещё не означает, что каждый builder нужен в повседневном коде. В dascript уже есть изменяемые переменные, генераторы, операции над коллекциями, корутины и async. Для многих задач они удобнее:

Задача С чего я бы начал
Изменять состояние Обычный var и передача состояния по ссылке
Передавать окружение или вести журнал Параметры функций, захваты, массив или logger
Преобразовать и отфильтровать коллекцию for, генератор массива, daslib/linq или daslib/functional
Выдавать последовательность значений Обычный генератор
Описать грамматику dasPEG
Подождать следующий кадр Стандартная корутина или [async]

Builders становятся интереснее, когда управление хочется выразить именно ходом исполнения кода: между шагами есть зависимые вычисления, ветвления, раннее отсечение, ожидания или ресурсы. Например, следующее правило парсера зависит от уже прочитанного значения; поиск должен отсечь неудачную ветку.

Конкретные билдеры могут добавлять абстракцию и иметь накладные расходы, другие просто перестраивают код.

Task: общий API для задач

Task даёт типизированный результат, ожидание других задач, статусы выполнения, отмену, таймауты и композицию. TaskBuilder работает с задачами, возвращающими значение, а TaskResultBuilder дополнительно распространяет ошибки Result: после неудачного шага остаток блока пропускается.

Задача создаётся отложенной: её тело начинает выполняться при первом опросе. Если очередная операция ещё не готова, управление возвращается вызывающему коду. Когда она завершится, выполнение продолжится с места ожидания. Готовый результат сохраняется, повторный опрос не запускает тело заново.

Derive#

Derive генерирует операции по описанию структуры. Кроме отладочного вывода, сравнения и хеширования, здесь есть builder, валидация и JSON-сериализация. Можно один раз описать поля и правила, а затем использовать их и при создании объекта в коде, и при загрузке данных.

Сеттеры генерируются из имён полей. При derive_build проверяется наличие обязательных полей, применяются значения по умолчанию и выполняется валидация. Если не задать имя или передать здоровье 150, готового игрока не будет — результат содержит none и ошибки. Черновик можно исправить и собрать повторно. Если здоровье вообще не задавать, builder возьмёт 100 из инициализатора структуры.

Для маленькой структуры с заранее известными значениями обычный Player(name="Alice", health=85) проще. Builder полезнее для редактора или формы, где поля заполняются постепенно, а на выходе нужен проверенный объект с диагностикой.

При чтении проверяются форма данных и типы полей, затем правила валидации. Ошибки содержат путь к полю, например player.health. Успешное чтение возвращает структуру непосредственно в loaded.value; у builder значение обёрнуто в Option. Сама сериализация валидацию не запускает — здесь ей передаётся уже проверенный результат сборки.

@json_name задаёт внешнее имя поля. @json_default=100 позволяет пропустить здоровье в JSON; это отдельное правило от обычного health : int = 100, которое использует builder. Без JSON-настройки поле при чтении было бы обязательным даже с инициализатором в структуре.

Потенциальная польза — конфиги, сохранения, игровые редакторы и обмен данными с инструментами. Список полей и правила проверки остаются рядом с моделью, не приходится вручную повторять их в builder, загрузчике и сериализаторе.
